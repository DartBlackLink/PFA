## C4 nivel 1: contexto

```mermaid
flowchart LR
    A[Administrador] --> S[EcoLogistica]
    R[Repartidor] --> S
    S --> M[Proveedor de recorrido OSRM]
    S --> T[Mapa base OpenStreetMap]
```

El administrador registra datos y asigna pedidos. El repartidor consulta sus asignaciones. El docente evalúa el producto y es interesado del proyecto; no es un usuario operativo. El cliente destinatario es una entidad del pedido dentro de este incremento.

## C4 nivel 2: contenedores

```mermaid
flowchart TD
    A[ADMIN] --> W[Cliente Flutter Web]
    R[REPARTIDOR] --> W
    W -->|REST JSON y Bearer| API[FastAPI Python]
    API -->|SQLAlchemy y psycopg| DB[(PostgreSQL 16)]
    API -->|HTTP: recorrido vial| OSRM[OSRM]
    W -->|Teselas| OSM[OpenStreetMap]
```

En ejecución local: Web 8080 y API 8000; la copia de entrega documenta Web 8081/API 8001 para operar de forma aislada. CORS enumera los orígenes permitidos. La API protege rol/propiedad y mantiene el estado de acceso en PostgreSQL. El backend solicita el recorrido; el navegador presenta geometría y marcadores.

## UML: secuencia de login y RN-023

```mermaid
sequenceDiagram
    participant U as Web por rol
    participant API as API identidad
    participant DB as PostgreSQL
    U->>API: POST auth/login
    API->>DB: Bloquear fila del identificador HMAC
    alt Bloqueo vigente
        API-->>U: 429 y Retry-After
        U->>U: Contador y boton deshabilitado
    else Puede intentar
        API->>API: Verificar credenciales
        alt Fallo
            API->>DB: Incrementar y fijar espera 5/10/300 s
            API-->>U: 401 o 429
        else Acceso valido
            API->>DB: Reiniciar fallos
            API-->>U: JWT y rol
            U->>API: GET auth/me al restaurar sesion
        end
    end
```

## UML: secuencia de asignación

```mermaid
sequenceDiagram
    participant A as ADMIN Web
    participant API as FastAPI
    participant DB as PostgreSQL
    participant G as OSRM
    A->>API: POST routes con recursos y pedidos ordenados
    API->>API: Verificar identidad y rol
    API->>DB: Bloquear recursos y pedidos
    API->>API: Validar activos, coordenadas, estado y peso
    API->>G: Solicitar recorrido desde origen por las paradas
    alt Recorrido valido
        G-->>API: Geometria, distancia y duracion
        API->>DB: Ruta, detalles y estado ASIGNADO en una transaccion
        API-->>A: 201 con detalle
    else Error del proveedor
        API-->>A: 503 sin confirmar asignacion
    end
```

## Casos de uso por actor

Representación funcional mediante nodos redondeados Mermaid, con actores y límite del sistema; complementa los diagramas UML de clases/secuencia.

```mermaid
flowchart LR
    A[Administrador]
    R[Repartidor]
    subgraph S[EcoLogistica: incremento Web/API]
        L([Iniciar y cerrar sesion])
        V([Gestionar flota])
        D([Gestionar repartidores])
        P([Registrar y consultar pedidos])
        AS([Asignar pedidos y recorrido])
        M([Consultar ruta y detalles])
    end
    A --> L
    R --> L
    A --> V
    A --> D
    A --> P
    A --> AS
    A --> M
    R --> M
```

Precondiciones: identidad vigente y rol permitido. ADMIN consulta las rutas globales; REPARTIDOR consulta solo su perfil/rutas. Entradas, validaciones y alternativas se especifican en RF, backlog y OpenAPI. El mapa representa una ruta planificada con orden elegido por el administrador.

## Decisiones y evolución de arquitectura

La arquitectura del producto se amplía por los incrementos del [roadmap](../02%20Planificaci%C3%B3n/02%20Artefactos%20Jira%20V_1_2_0.md). Cada módulo se incorpora mediante su contrato, migración y prueba de aceptación. El diseño de requisitos conserva el objetivo VRPTW/Green VRP y las funciones de sostenibilidad de la consigna. El cliente Android/iOS se organiza en `apps/mobile`, con API común y verificación por plataforma.
