## Contrato de calidad

Cada escenario usa Fuente → Estímulo → Entorno → Artefacto → Respuesta → Medida. Los umbrales identificados como objetivos adicionales son decisiones de diseño verificables del estudiante; no se atribuyen a la consigna. ## RNF-01 - Rendimiento

| Elemento | Especificación |
| --- | --- |
| Fuente | Administrador o evento operativo |
| Estímulo | solicitud de optimización o reoptimización |
| Entorno | entorno de benchmark con hardware y versiones registrados |
| Artefacto | API y algoritmo genético |
| Respuesta | obtener plan factible o diagnóstico; medir cálculo completo hasta persistencia |
| Medida | ≤45 s con 150 pedidos/15 vehículos; <30 s para reoptimizar ese tamaño |
| Enabler | EN-004 |
| Método y evidencia | Ejecutar cinco semillas por cada dataset fijo de 10, 50 y 150 pedidos; informar máximo, mediana y factibilidad. Todas las ejecuciones deben respetar el umbral; conservar datos, semillas y resultados. |

## Datos mínimos del expediente de prueba

Registrar identificador de caso, RF/RNF, versión de código, entorno, dataset/semilla, pasos, esperado, obtenido, duración, resultado y evidencia. La cobertura ≥80% del DoD se calcula sobre lógica testeable con exclusiones justificadas; no se confunde con 80% de requisitos. Las mediciones de carga, aceptación y accesibilidad tienen sus propios resultados.

## Control de intentos de login - RN-023

Aplica a ADMIN Web y REPARTIDOR móvil, y al acceso CLIENTE al habilitar RF-09. Credenciales: email normalizado y contraseña. La API aplica la política por identificador, con estado compartido persistente y actualización atómica; el contador visual refleja el plazo devuelto por el servidor.

| Fallos consecutivos procesados | Espera antes de otro intento |
| --- | --- |
| 1 o 2 | Sin bloqueo temporal |
| 3 | 5 segundos |
| 4 | 10 segundos |
| 5 o más | 300 segundos (5 minutos) |

Durante la espera la API responde 429 y Retry-After con los segundos restantes; el cliente deshabilita Iniciar sesión y muestra «Inténtalo de nuevo en N segundos», o mm:ss para 5 min. La espera empieza al procesar el fallo, no al abrir la pantalla. Solicitudes mientras está bloqueado no incrementan intentos ni extienden el plazo. Una recarga, cambio de dispositivo o reinicio de API no evita el bloqueo; rehidratar el contador desde la respuesta. Credenciales correctas durante el bloqueo también esperan.

Al vencer el plazo se permite un intento: otro fallo escala según la tabla, mientras un login correcto reinicia intentos y bloqueo. El contador no se reinicia solo por cumplir la espera. Contar únicamente fallos de credenciales procesados; errores de red o validación local no suman. Mantener respuesta genérica para cuentas existentes o inexistentes, no revelar contraseñas/tokens y registrar auditoría. El cierre de sesión elimina el token local; una sesión restaurada valida vigencia y rol. Protección adicional por origen y recuperación de acceso se gestionan por separado de esta secuencia.

Pruebas de frontera: fallo 3/4/5, instante anterior y posterior al desbloqueo, recarga, dos dispositivos, concurrencia, credenciales correctas durante espera y reinicio después de éxito. El reloj del servidor decide; aceptar únicamente respuestas consistentes en Web y móvil.
