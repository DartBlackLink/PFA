## 2. Propósito

Este documento separa dos conceptos que no deben confundirse:

1. **Alternativas o propuestas similares de stack**, utilizadas para comparar enfoques tecnológicos.
2. **Propuesta real de desarrollo del estudiante**, que será implementada con **Flutter Web** y **Flutter móvil como aplicaciones separadas**.

La selección de Flutter corresponde a una decisión de implementación del proyecto. Los stacks comparativos se mantienen como alternativas de referencia y no representan la tecnología final elegida.

## 4. Propuesta real de desarrollo

### 4.1 Aplicación Web

- **Tecnología:** Flutter Web.
- **Lenguaje:** Dart.
- **Proyecto:** independiente.
- **Usuarios principales:** administrador, operador logístico y gerencia.
- **Funciones principales:**
  - gestión de flota;
  - gestión de pedidos;
  - gestión de conductores;
  - gestión de clientes;
  - configuración y ejecución de optimización;
  - visualización de rutas;
  - dashboard;
  - reportes;
  - administración del sistema.

### 4.2 Aplicación móvil

- **Tecnología:** Flutter.
- **Lenguaje:** Dart.
- **Proyecto:** independiente de Flutter Web.
- **Usuarios principales:** conductores.
- **Funciones principales:**
  - autenticación;
  - consulta de ruta asignada;
  - consulta de entregas pendientes;
  - navegación de la secuencia de entregas;
  - visualización de alertas;
  - reporte de incidentes;
  - actualización de estados operativos.

> Las dos aplicaciones se consideran **clientes diferentes**. No se documentan como una sola aplicación responsive.

## 5. Backend común

Flutter cubre la capa cliente. Para centralizar reglas, persistencia, seguridad e integración se propone un backend común:

- **Python + FastAPI** para API REST.
- **PostgreSQL** para persistencia.
- **OpenAPI/Swagger** para contrato de servicios.
- Servicio/módulo de optimización implementado en Python.
- Adaptador para mapas y tráfico.
- Generación de reportes desde backend.

Esta decisión permite aprovechar Python para el problema de optimización sin impedir que ambas interfaces se desarrollen completamente en Flutter.

## 8. Justificación de Flutter

Flutter se selecciona porque permite mantener un ecosistema Dart coherente en ambas interfaces y construir:

- un cliente web para tareas administrativas;
- un cliente móvil específico para el conductor;
- componentes y patrones de interfaz consistentes;
- pruebas automatizadas del cliente;
- separación clara entre presentación y lógica de negocio centralizada en la API.

La decisión de mantener **dos proyectos Flutter separados** permite que la navegación, permisos, experiencia de usuario y ciclo de despliegue del sistema web y de la aplicación móvil evolucionen de manera independiente.

## 10. Criterios de sostenibilidad técnica

- evitar solicitudes redundantes desde ambos clientes;
- aplicar paginación y carga bajo demanda;
- minimizar transferencia de datos;
- reutilizar recursos y assets optimizados;
- medir rendimiento en Flutter Web y Flutter móvil de forma independiente;
- ejecutar la optimización en backend para no sobrecargar dispositivos móviles;
- evitar dependencias innecesarias.

## 11. Decisión final

La propuesta tecnológica del proyecto queda establecida como:

> **Flutter Web + Flutter móvil (aplicaciones separadas) + FastAPI/Python + PostgreSQL**, con una API común para centralizar la lógica de negocio y el motor de optimización.
