## Alcance y fuentes de evidencia

EcoLogística Huancayo es la propuesta del estudiante; el escenario de evaluación sigue siendo Lima (San Juan de Lurigancho, El Agustino, Santa Anita y Ate), con RF-01 a RF-10, RNF-01 a RNF-07 y RES-01 a RES-12. Los mapas de Huancayo son una demo adicional.

Arquitectura objetivo: Web ADMIN con preferencias CLIENTE (RF-09), móvil REPARTIDOR, FastAPI y PostgreSQL. Este documento define el diseño y sus criterios de validación. Las acciones de implementación, Jira, Figma y evidencias se coordinan en la guía de ajustes.

## Elicitación holística y ética

La fuente confirmada es análisis documental de las consignas; no existen entrevistas o investigación de campo acreditadas en los archivos revisados. Se distinguen necesidades de administrador, repartidor y cliente; el docente evalúa conformidad y la gerencia del caso revisa costos y sostenibilidad. Las validaciones futuras usarán datos sintéticos, consentimiento para participación y mínimo acceso a datos personales. Cada cambio debe registrar fuente, RF afectado y decisión en el historial.

Método de validación previsto: revisión de requisitos con docente, recorrido de mockups por rol, dataset controlado de Lima, pruebas de aceptación por historia y análisis de datos faltantes. Una entrevista futura se documentará con fecha, participante autorizado y hallazgos; no se declarará realizada antes de contar con evidencia.

## Especificación y criterios de aceptación

### RF-01 - Gestión de flota

Registrar, consultar, actualizar e inactivar vehículos identificados por placa, con tipo, capacidad en kg, consumo en km/L, factor de emisión en kg CO₂/km y año de fabricación. Conservar historial de asignaciones.

| Campo | Contrato |
| --- | --- |
| Actor | Administrador |
| Canal | Web |
| Prioridad | Alta |
| Precondición | usuario ADMIN activo; para alta no se exige que el vehículo exista |
| Historia | US-003 |
| Reglas | RN-001, RN-002, RN-016 |

**Ruta Gold**

- **Dado** una placa no registrada y un administrador autenticado.
- **Cuando** registra una camioneta de 800 kg, 10 km/L y 0.18 kg CO₂/km.
- **Entonces** se persisten todos los campos y se devuelve su identificador.

**Ruta feliz alternativa**

- **Dado** un vehículo existente sin ruta activa.
- **Cuando** el administrador corrige el consumo a 12 km/L.
- **Entonces** se guarda el nuevo valor y las métricas históricas mantienen sus parámetros originales.

**Ruta infeliz**

- **Dado** la placa ABC-123 ya registrada.
- **Cuando** se intenta registrar otra unidad con esa placa o capacidad cero.
- **Entonces** se rechaza la operación con error de campo y no se crea un duplicado.

### RF-02 - Gestión de pedidos

Registrar y actualizar pedidos con cliente, dirección, punto de referencia, latitud/longitud, peso, volumen, ventana de entrega, prioridad EXPRESS/ESTANDAR/ECONOMICO y producto PERECEDERO/NO_PERECEDERO. Separar borrador de pedido listo para planificar.

| Campo | Contrato |
| --- | --- |
| Actor | Administrador |
| Canal | Web |
| Prioridad | Alta |
| Precondición | ADMIN activo y cliente identificado |
| Historia | US-005 |
| Reglas | RN-003, RN-004, RN-017 |

**Ruta Gold**

- **Dado** un cliente y coordenadas confirmadas en Lima.
- **Cuando** se registra un pedido de 10 kg y 0.1 m³ con ventana 09:00 a 11:00.
- **Entonces** se guarda el pedido con datos completos y queda disponible para planificación.

**Ruta feliz alternativa**

- **Dado** una dirección sin nomenclatura estándar.
- **Cuando** se agrega una referencia y se confirma el punto en el mapa.
- **Entonces** se conserva dirección y referencia, y se habilita planificación al confirmar las coordenadas.

**Ruta infeliz**

- **Dado** un pedido con ventana invertida o ubicación sin resolver.
- **Cuando** se intenta guardar la ventana inválida o incluir el borrador en optimización.
- **Entonces** se rechaza la ventana inválida y el pedido sin coordenadas queda excluido con causa explícita.

### RF-03 - Generación de rutas optimizadas

Generar y persistir un plan de reparto mediante algoritmo genético para VRPTW/Green VRP. Considerar distancia, tiempo, combustible, CO₂ y tardanza; respetar capacidad, disponibilidad, descansos y zonas restringidas. Reportar pedidos no asignados y su causa.

| Campo | Contrato |
| --- | --- |
| Actor | Administrador / Sistema |
| Canal | Web + API |
| Prioridad | Alta |
| Precondición | pedidos georreferenciados, recursos activos y parámetros versionados |
| Historia | US-007 |
| Reglas | RN-002, RN-005, RN-006, RN-011, RN-016 |

**Ruta Gold**

- **Dado** un dataset factible de hasta 150 pedidos y 15 vehículos.
- **Cuando** el administrador ejecuta el algoritmo genético.
- **Entonces** se obtiene en ≤45 s un plan sin violaciones duras, con secuencia, ETA, métricas, semilla y parámetros persistidos.

**Ruta feliz alternativa**

- **Dado** el proveedor de tráfico no disponible y datos manuales fechados.
- **Cuando** se calcula un plan con la alternativa autorizada.
- **Entonces** el plan identifica origen y antigüedad del tráfico y no lo presenta como tráfico en tiempo real.

**Ruta infeliz**

- **Dado** demanda que excede capacidad o disponibilidad.
- **Cuando** se solicita una optimización.
- **Entonces** se reportan pedidos no asignados con causa y ninguna ruta inválida se marca como factible.

Sin registros válidos, mostrar no calculable; la puntualidad prevista usa ETA y se etiqueta como estimación.

### RF-07 - Reoptimización dinámica

Recalcular y versionar el plan pendiente ante nuevo pedido, cancelación, accidente o avería; preservar entregas completadas y posición confirmada. Registrar eventos y notificar la nueva asignación al repartidor.

| Campo | Contrato |
| --- | --- |

| Precondición | plan activo, evento identificado y posición con antigüedad visible |
| Historia | US-010, US-011 |

**Ruta Gold**

- **Dado** una ruta activa y una avería reportada.
- **Cuando** se confirma el evento y se ejecuta reoptimización.

**Ruta feliz alternativa**

**Ruta infeliz**

## Cobertura del MVP

El núcleo de aceptación comprende RF-01 a RF-07. La meta académica de al menos 70% sobre diez RF se acredita por requisitos completos y pruebas aprobadas, no por pantallas ni porcentaje de líneas de código. RF-08 proporciona datos necesarios del conductor, aunque figure como complementario. RF-09 y RF-10 permanecen en backlog; su cumplimiento incluye todos sus canales y cálculos. Un RF parcial no cuenta como completado. Al corte de esta revisión no se certifica ningún porcentaje ejecutado porque faltan pruebas de aceptación.

## Precondición transversal de acceso

ADMIN y REPARTIDOR inician sesión con email/contraseña y política RN-023: tercer fallo 5 s, cuarto 10 s, quinto y posteriores 300 s; la API controla el plazo, el cliente muestra el contador y un login correcto reinicia la secuencia. CLIENTE utiliza la misma política al habilitar RF-09. La sesión y la autorización por recurso preceden a toda operación protegida.
